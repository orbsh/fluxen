# ADR 0018: 力导向图的渲染层——场景抽象（three-d），边是世界空间几何

状态：已接受（2026-10-26 用户裁决后实施）
日期：2026-10-26
仓库：fluxen

## 背景

原生力导向组件（ADR 0017 之后由 `crates/forcegraph` 承担）最初的渲染器是手写
WebGL2：节点是实例化球体，边是**在裁剪空间展开的屏幕像素四边形**。那是"让 2.5px
的线在真实驱动上可见"的最省事做法（`gl.LINES` 的线宽被钳到 1 设备像素）。

用户 2026-10-26 判定这条路不可接受：

> 边是在二维投影上画的？这不可接受，因为后续可能会有其它需求，现在只是打好基础。
> 引入 three-d 的 41KB 我认为可以接受，后续功能复杂了，还是要有中间层，不然不好理解
> 和维护。

同时给出了这一层要承接的目标（全文见 `docs/ideas/graph-visuals.md`）：节点与边的霓虹
呼吸、边的流动、节点光晕；图中出现非节点非边的元素；节点放大成迷你星球；图放进一个
场景；整站 3D 化、对话框 pin 在场景一侧、其它 UI 嵌进图里；主干 + 藤蔓的形态表达。

这些需求没有一条能落在屏幕空间图元上：流动需要沿边长的参数，光晕需要深度与后期，
藤蔓是曲线，主干是世界尺度上的粗细。所以问题不是"要不要更漂亮的库"，而是**这一层
的形状错了**。

## 决策

1. **渲染层用 three-d**（0.19，`default-features = false`，即 glow / WebGL2）：
   它提供场景对象、材质、光照、渲染目标、射线拾取与文字，正好是上面那些需求所
   构成的层。canvas 仍归 DOM，three-d 只拿到它已经创建的 GL context
   （`Context::from_gl_context`），不接管事件循环。
2. **画图 API 是 WebGL2，不是 WebGPU。** 二者是两件正交的事：three-d 只有 glow；
   wgpu 在 Linux 桌面浏览器仍是有条件的（Chrome 需较新版本 + 特定 GPU，Firefox
   Linux 未默认开启），且 Rust 侧没有 three-d 这样的成熟场景层。缝留着，换 API 时
   换的是缝之后那一侧。
3. **边是世界空间几何。** 单位四边形（u 沿边、v 横向）经仿射矩阵映射成平行四边形，
   横向宽度由 `frame` 按该边中点深度把像素宽度换算成世界单位。于是：线宽在屏幕上
   恒定、几何在场景里有深度、被节点正确遮挡，而 `u` 就是边长参数——后续的流动、
   藤蔓、主干都长在这个参数上。
4. **Frame 缝。** `frame::build(camera, viewport, dpr, scene, style) -> Frame`
   是纯函数：输出 viewer（位置、view/projection 矩阵、视口）与两组实例
   （节点的变换+颜色、边 的变换+颜色）。所有"画成什么样"的判断都在这里，宿主侧可
   测、无需 GPU；后端只负责上传与两次 draw call。
5. **旧的手写 WebGL2 渲染器删除。** 不留双后端：两套渲染路径正是要消掉的维护负担，
   而且它的边绘制方式本来就要废弃。
6. **相机仍然只有一个。** 拾取、标签、标签层用 `camera.rs` 的 CPU 投影；绘制让
   `FrameViewer` 实现 `three_d::Viewer`，喂同一个相机导出的矩阵。一个相机，两处
   消费者，不会分叉。

## 后果

- **体积实测**（真实组件，非玩具工程）：wasm 2,348,320 → 2,739,031 B（+390,711，
  +16.6%）；gzip 709,984 → 851,259 B（+141,275，+19.9%）。先前"一个受光球体"的
  玩具估算 +41 KB gzip 低估了三倍多：真组件还带上了 PBR 材质、光照、渲染目标与效果
  链的着色器字符串。绝对值可接受，代价要记住。
- **three-d 没有 bloom。** 光晕/霓虹要自己写一遍后期（亮部提取 + 可分离模糊 + 加法
  合成，挂在它的 `Effect` 上）。接入不等于拿到光。
- **没有默认 MSAA/FXAA。** 球体与边缘会有锯齿，后续可挂 `FxAAEffect` 或自建 MSAA
  目标。
- **碰撞半径不再读相机。** 原来"按当前缩放把像素半径换算成世界半径"与常驻 auto-fit
  构成正反馈：云变大 → 相机后退 → 世界半径变大 → 云更大。实测数秒内跑到 17 万世界
  单位（`d=165290 r=174848 ppu=0.00`）。现在碰撞是布局自身的性质（由 link distance
  推出），与视口无关；节点在屏幕上仍按像素定尺寸，两者不再耦合。
- **布局与视口解耦**这件事写下来，因为它不只修一个 bug：一个图的形状不该因为有人
  滚了滚轮而改变。

## 屏幕恒定的光（2026-10-27）

节点的球径是像素值，光晕、选中环都是它的固定倍数：光晕 5.45 倍半径、选中环贴在光晕
边缘。选中不改变光晕——同样大小、同样亮度，选中只是外面多一圈虚线环。换算成世界单位时按该节点自己的深度除一次，所以三样东西在屏幕上的尺寸都不随
缩放变化，比例也不变——球永远比光晕小，光晕永远比环大。

这是有意的，效果也正来自它：**缩小时相邻节点的光晕会互相叠在一起，图变成一片云。**
云不是瑕疵，是这张图用来表达密度的手段——距离远到看不清边的时候，读者看到的应该是
哪里亮、哪里稀，而不是一堆缩成针尖的点。若尺寸改成世界恒定，放大时球会吞掉整张图，
缩小时又会全部消失，两种都不成立。

光的结构分两层：**核心**（紧贴球、指数 5 的陡衰减、向白色提亮）是光源，**光晕**
（4.6 倍半径、指数 1.4 的缓衰减）是它的外溢。只有外溢时，画面读作"一块匀亮的软盘"；
加上核心才有梯度，密集处多个核心叠加会自己烧起来。核心只在深色主题存在——浅底上
没有比它更亮的东西，白色核心叠在白页面上等于不存在，压暗它又只是第二个球。

高亮也是这样一层：**不加暗、只加亮**。早先的做法是把没被点名的节点和边乘 0.3–0.35，
读起来像"只有这一处重要、整张图是背景"。现在被点名的节点加罩（选中环），从它出发
`reach_hops` 条边以内的节点和边提亮加粗（`highlight_reach`，默认开、1 跳），其余保持
原样。镜头也随之取景到"被点名 + 可达"这一组，而不是只框住被点名的那一个——只框住
一个会把图放大到其余部分全出画。

同样是这个理由，边画成**圆管**而不是扁带：扁带正对相机是一条带宽、侧对相机是一条
发丝，弯曲之后同一条边在自己在不同位置的宽度都不一样。圆管横截面处处相同，弯到哪
个角度都还是一个宽度，这才是"光线"该有的样子。

## 实测（34 点 / 44 边，220×473 视口，headless chromium + SwiftShader）

- 稳定：`d=565 r=204 ppu=15 cl=11.5`，alpha 收敛到地板。
- 边确实被画出：真边中点 72/80 有墨，非边中点 32/80（后者来自与真边交叉或擦过节点）。
- 隐藏 DOM 覆盖层后彩色像素 6888（节点与边都在）。
