# 交互的绘制模式

一份给「往视图里画东西的那一方」看的文档：一次交互从人动手到画面上出现东西，中间依次发生什么，
以及哪些决定归应用、哪些归渲染器。它不是 accrete 的语法手册（那是 `external-integration.md`），
也不描述某个具体应用——只描述形状。

全文的前提是一条分工：**渲染器没有业务逻辑。** 它执行操作，不解释动作。所以「我发出去的消息出现了」
「提交表单后出现一行提示」这类事情，无法由客户端推断，也不能由客户端乐观插入：客户端不知道
一条消息是一行、这一行该进哪个列表、长什么样子。**显示逻辑归应用，机制归渲染器。**

## 一次交互的五步

以对话里发一条消息为例，顺序就是实现里真实的顺序：

1. **客户端发事件。** 载荷带人做了什么（文字），如果这一方要画面，还带要画进哪些槽
   （`rack` = 行列表，`text` = 区域）。客户端不画。
2. **应用先把这件事变成事实。** 落盘（那一刻顺带拿到这一轮的 id）。没有这一步，后面说的都没有依据。
3. **应用先说话，再干活。** 先发一个回执（`{turn}`：这条回执让客户端能把它自己发的那句话和后面的
   答案对上号），然后**一批**操作：把用户这一行 append 进 `rack`、建好答案要流进去的区域、
   append 读这个区域的气泡。批内顺序是语义：填充区域的 patch 必须在建它的 `set` 之后。
4. **这时才开始干活。** 答案的每一段只 `patch` 第 3 步建好的区域，不重画舞台。
5. **结束要说出来。** `done`，或带原因的 `error`。失败不撤销第 3 步：用户那句话留在屏上是事实。

按钮、表单同理：点一下，客户端发事件，应用回答以操作（可能只是 append 一行提示）。没有哪一步是
客户端能自己完成的。

## 容器形状归应用

同一批行在一个 `rack` 里，彼此的区别是行自己的容器：对话流里用户行靠末端对齐并带强调色，
回复行铺满、无强调色。这个差别**是帧携带的类名**，不是渲染器的知识——一个从没听说过「对话」的
渲染器照样把两者画对。

行身份在数据里（`data.id`），复用的版式在 `rack.item`（ADR 0020），摆法在 `attrs.view`（ADR 0024）。
应用决定行是什么、装什么；渲染器决定这些行怎么摆、怎么进出场。

## 帧里没有的东西

- **停多久、要不要淡入淡出、跟不跟尾巴。** 那些是渲染器的词汇（ADR 0024），应用只送行；
- **「通知」「横幅」「聊天气泡」这类型名。** 它们是值的组合，不是类型（ADR 0024 §8）；
- **本地乐观插入。** 见开头：客户端不知道这条该画成什么。

所以「用户发了消息，他自己看得见吗」的答案是：看得见，因为应用在他发出的那一刻送了那一行；
不是因为客户端猜的。

## 这条模式对应用的要求

1. 事实先落，画面后发——否则画面说的东西没有依据；
2. 画面在**干活之前**发——否则一次慢调用就表现为「发了没反应」，一次失败就表现为「发了却像没发」；
3. 每一帧带同一个归属 id（如这一轮的 `turn`），让客户端把同一次交互的后续都挂回那一行；
4. 只送人需要读的（见 gravity ADR-0010：工具调用的参数与结果留日志，界面上至多发标题和状态）。
